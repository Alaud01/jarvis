# Keep Codex state inside a Jarvis-owned runtime

Jarvis integrates ChatGPT subscription access through a bundled Codex app-server, but runs it with a dedicated `CODEX_HOME`, state database, working directory, and account lifecycle under Jarvis application data. Jarvis conversations remain the only user-visible conversation model and map to private app-server threads; Jarvis never reads, copies, or writes the user’s normal `~/.codex`, and one-off work uses ephemeral threads. This preserves the supported app-server protocol while avoiding the cross-client auth and thread overlap that would result from sharing the user’s Codex installation or state directory.

## Amendment: follow Codex Switcher's active account

When Codex Switcher is installed (`~/.codex-switcher/accounts.json` exists), Jarvis uses the account Codex Switcher has selected instead of its private login. Jarvis only reads `~/.codex/auth.json`. Before each Codex request it supplies that file's access token to the private app-server through `account/login/start` with `chatgptAuthTokens`. The app-server holds this external auth in memory only. As a result, Jarvis never writes, refreshes, or revokes the Switcher-managed credentials, and its private `auth.json` stays untouched. Threads, state databases, and the working directory remain private.

Jarvis re-reads the file before each Codex request and supplies any changed token, so a Switcher account change takes effect without restarting the app-server. Codex keeps each thread's model connection open across turns, authenticated as whichever account opened it, so Jarvis binds the account identity into the persistent thread's fingerprint. After a switch, the conversation is replayed into a fresh thread on the new account. Codex opens a thread's connection when the thread is created or resumed, so Jarvis prepares the thread first and then reserves the account for the turn. A generation counter increases whenever the supplied account changes. If it changed at any point during preparation, including during replay compaction and even if it changed back, the prepared thread may hold another account's connection. Jarvis therefore discards that thread and prepares a new one. While any turn holds a reservation, a switch is deferred rather than awaited, which avoids deadlocking nested requests; it applies at the next request after those turns finish. As long as reservations keep overlapping, the switch keeps being deferred. Running turns stay on the account they started with. If the backend rejects a reserved turn's token after the Switcher account changed, Jarvis fails that turn and asks the user to resend rather than moving its output and tools to another account. A refreshed token for the same workspace and user remains allowed. When the backend rejects a token, the app-server asks for a new one with `account/chatgptAuthTokens/refresh`. Jarvis answers with the file's current token, and Codex retries only once with it. Jarvis never refreshes tokens itself. If the login is still rejected, the error asks the user to refresh it in Codex Switcher or the Codex app.

Accounts are identified by ChatGPT workspace and user id, so a routine token refresh is not treated as an account change. A turn that fails with `usageLimitExceeded` is retried once on the newly selected account only when the account has actually changed and the failed attempt streamed no output and ran no tools. Otherwise, the error tells the user to switch in Codex Switcher. Browser login and `account/logout` are disabled in this mode. Set `JARVIS_CODEX_PRIVATE_AUTH=1` to keep the private-login behavior.
